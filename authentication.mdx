Veyra uses a **two-tier authentication model** that separates administrative operations from telemetry ingestion. JWT tokens let you manage your account and projects through the API. API keys — prefixed with `veyra_` — let your services send events, heartbeats, and incidents. Understanding which credential to use where is the foundation of a secure Veyra integration.

---

## JWT tokens (Account management)

JWT tokens are issued by the Veyra authentication endpoints when you log in. They are short-lived, bearer-style tokens that authorize administrative actions: creating and listing projects, generating API keys, and managing account settings.

Pass a JWT token in the `Authorization` header as a `Bearer` token on any management endpoint.

### Obtaining a token

<Tabs>
  <Tab title="curl">
    ```bash
    curl -X POST https://api.strixhost.xyz/v1/auth/login \
      -H "Content-Type: application/json" \
      -d '{
        "email": "dev@example.com",
        "password": "supersecure123"
      }'
    ```
  </Tab>
  <Tab title="JavaScript">
    ```javascript
    const response = await fetch("https://api.strixhost.xyz/v1/auth/login", {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
      },
      body: JSON.stringify({
        email: "dev@example.com",
        password: "supersecure123",
      }),
    });

    const { token } = await response.json();
    console.log("JWT token:", token);
    ```
  </Tab>
</Tabs>

The response body includes a `token` field containing your JWT. Store it securely for use in subsequent management requests.

### Using a JWT token on a protected endpoint

Here's an example of creating a new project using a JWT token:

```bash
curl -X POST https://api.strixhost.xyz/v1/projects \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer YOUR_JWT_TOKEN" \
  -d '{
    "name": "My Backend",
    "environment": "production",
    "heartbeatInterval": 60000
  }'
```

<Info>
  JWT tokens are time-limited. If you receive a `401 Unauthorized` response on a management endpoint, your token may have expired — log in again to obtain a fresh one. For long-running automation scripts, implement a token refresh or re-authentication step before making management calls.
</Info>

## API keys (Telemetry)

API keys are generated per-project and are the credential your running services use to send data to Veyra. Every API key is prefixed with `veyra_` so they're easy to identify and to configure secret-scanning rules around.

Use API keys for all telemetry operations: sending events, pinging heartbeat endpoints, and triggering incidents.

### Generating an API key

You need a valid JWT token to generate an API key. Replace `YOUR_PROJECT_ID` with the ID of the project you want to associate the key with:

```bash
curl -X POST https://api.strixhost.xyz/v1/projects/YOUR_PROJECT_ID/keys \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer YOUR_JWT_TOKEN" \
  -d '{
    "name": "Production API Key"
  }'
```

The response includes the full `veyra_`-prefixed key. This is the **only time** the plaintext key will be returned.

<Warning>
  **API keys are shown exactly once.** Veyra does not store the plaintext value after generation. If you lose a key, revoke it and generate a replacement. Always save newly generated keys to a secrets manager or environment variable before closing the session.
</Warning>

### Using an API key in a telemetry call

Pass your API key as a `Bearer` token in the `Authorization` header, just like a JWT — the `veyra_` prefix tells Veyra to treat it as a project-scoped telemetry credential:

```bash
curl -X POST https://api.strixhost.xyz/v1/events \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer veyra_YOUR_API_KEY" \
  -d '{
    "level": "error",
    "message": "Database connection failed",
    "source": "Payment-Service",
    "environment": "production"
  }'
```

And a heartbeat ping using the same key:

```bash
curl -X POST https://api.strixhost.xyz/v1/heartbeats/YOUR_PROJECT_ID \
  -H "Authorization: Bearer veyra_YOUR_API_KEY"
```

## Choosing the right credential

| Operation | Credential type |
|---|---|
| Register a new account | None required |
| Log in | None required |
| Create or list projects | JWT token |
| Generate or revoke API keys | JWT token |
| Send events | API key (`veyra_`) |
| Send heartbeat pings | API key (`veyra_`) |
| Trigger or update incidents | API key (`veyra_`) |

<Tip>
  A useful mental model: **JWT tokens are for humans and scripts that manage infrastructure.** **API keys are for services and daemons that report data.** If a credential needs to live inside a running process or be deployed to a server, it should be an API key — not a JWT.
</Tip>

## Security best practices

Follow these practices to keep your Veyra credentials secure:

**Store keys in environment variables.** Never hardcode a JWT token or API key directly in your source code. Load them at runtime from environment variables or a secrets manager:

```javascript
const apiKey = process.env.VEYRA_API_KEY;

const response = await fetch("https://api.strixhost.xyz/v1/events", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Authorization": `Bearer ${apiKey}`,
  },
  body: JSON.stringify({
    level: "info",
    message: "Service started",
    source: "Auth-Service",
    environment: "production",
  }),
});
```

**Never commit credentials to source control.** Add `.env` files to your `.gitignore` and enable secret-scanning on your repository. The `veyra_` prefix makes it easy to write a custom pattern for tools like GitHub Advanced Security or GitGuardian.

**Rotate keys if compromised.** If you suspect an API key has been exposed — in logs, a public repository, or a misconfigured deployment — revoke it immediately from your project settings and generate a replacement. Update all services using the old key before revoking it to avoid downtime.

**Use one key per service.** Generate a separate API key for each service or deployment environment. This limits the impact of a single key being compromised and makes it easy to rotate credentials for one service without affecting others.

**Treat JWT tokens as session credentials.** Don't store JWT tokens on disk or in long-lived configuration files. Obtain a fresh token at the start of any administrative script and discard it when the script completes.
